# 보안 모델과 한계

공격자는 ESB, 코드, 원본 후보를 알고 컨테이너를 변조할 수 있다. 비밀번호와 실행 환경은 보호된다고 가정한다. ESB는 외부 감사를 받은 표준 포맷이 아니다.

## 암호 구성

공개 헤더는 키 유도에 필요한 salt와 nonce prefix 및 고정 프로파일만 포함한다. 평문 해시·키·단순 비밀번호 검증값은 저장하지 않는다. 원본 HMAC은 파일마다 다른 키로 계산하고 FINAL 내부에서 AEAD로 암호화한다. 동일 원본과 비밀번호도 새 salt와 prefix로 다른 컨테이너가 된다. 공개 원본 해시만으로 일치 여부를 판단할 수 없지만 공격자는 비밀번호를 추측하여 META의 태그로 확인할 수 있다. Argon2id는 비용을 높일 뿐 이 공격을 없애지 않는다.

XChaCha는 16바이트 랜덤 prefix와 연속 64비트 인덱스로 24바이트 nonce를 만든다. AES는 레코드마다 별도 HKDF 키를 만들고, 4바이트 prefix와 인덱스로 12바이트 nonce를 만든다. 어떤 인증 실패에도 다른 스위트로 재시도하지 않는다. META, DATA, FINAL에 전역 인덱스를 사용하고 overflow는 오류다.

AES-GCM의 평문 한 레코드는 최대 2^22바이트(2^18개 16바이트 블록)이며 128비트 태그를 사용한다. [RustCrypto 0.10.3의 P_MAX](https://docs.rs/aes-gcm/0.10.3/aes_gcm/constant.P_MAX.html)보다 작다. 단일 메시지 제한과 한 키의 누적 사용량은 다른 제한이다. 이 구현은 한 파생 AES 키에 암호화 한 번만 수행하며 파일 전체에 같은 AES 키를 쓰지 않는다. 그러나 HKDF 출력 충돌의 확률, 총 레코드 수, 전체 위조 시도에 따른 다중 키 인증 한계가 사라지는 것은 아니다. 이 정책을 무제한 크기의 안전성 증명이라고 해석하지 않는다. 공개된 단일 키 GCM 사용량 권고를 다중 키 전체에 그대로 적용하거나 반대로 무시하지 않는다. [libsodium AES-GCM 설명](https://doc.libsodium.org/secret-key_cryptography/aead/aes-256-gcm)과 [RustCrypto 보안 주의사항](https://docs.rs/aes-gcm/0.10.3/aes_gcm/#security-notes)을 참조한다.

배포 지원 CPU는 x86_64/aarch64이다. 해당 AES 라이브러리는 하드웨어 가속 및 상수 시간 곱셈 CPU의 소프트웨어 구현을 제공한다. 그 외 CPU에서 AES 작업은 명시적으로 거부하며 조용히 다른 스위트로 바꾸지 않는다. 32비트 가변 시간 곱셈 CPU는 배포 지원 대상이 아니다.

## 파서와 자원

KDF 전에 64바이트 고정 헤더와 프로파일을 검사한다. 레코드 헤더는 읽은 뒤 타입·길이·예상 인덱스를 검사하여 공격자가 지정한 크기로 할당하지 않는다. Argon2 작업 메모리 64 MiB와 소수의 고정 청크가 필요하다. Argon2 할당은 fallible reserve로 실패를 반환하고 약한 KDF로 자동 변경하지 않는다. 일반 런타임/의존성의 모든 소규모 할당 실패를 복구한다고 보장하지 않는다. `fuzz/`는 KDF 없이 헤더 파서를 공격한다.

각 DATA는 인증 후 출력하며 마지막 FINAL, HMAC `verify_slice`의 상수 시간 비교, 크기·청크 수·EOF가 모두 맞아야 성공한다. 저수준 스트림 API 사용자는 검증 전 출력 격리를 책임진다.

## 파일 트랜잭션

Unix의 임시 디렉터리는 생성 시 0700, 파일은 0600이다. Windows는 랜덤 임시 디렉터리를 만들고 현재 프로세스 SID에만 상속 가능한 전체 권한을 부여하며 기존 상속을 제거한다. ACL 적용 실패 때 평문 파일을 만들지 않고 오류를 반환한다. Windows SID는 `whoami.exe`, DACL은 `icacls.exe`로 적용하므로 이 시스템 도구가 없는 제한 환경에서는 실패한다. 사용자 이름의 인코딩과 무관하게 SID만 ASCII로 검증한다.

대상 부모를 canonicalize하고 같은 파일시스템에 임시 파일을 둔다. flush/sync 후 `hard_link`로 목적지 이름을 생성한다. 이 연산은 이미 있는 파일·심볼릭 링크·하드링크를 덮어쓰지 않는다. 원자적 생성 직전 다른 프로세스가 목적지를 만들어도 실패한다. 하드링크를 지원하지 않는 파일시스템은 오류로 끝나며 덮어쓰는 rename 대안은 사용하지 않는다. 입력 파일 handle과 현재 경로의 파일 ID/inode, 크기와 수정 시각을 비교한다. 검사 직후 변경되거나 시각을 복원하는 모든 동시 변경을 탐지하는 스냅샷은 아니다.

입출력 부모 디렉터리는 신뢰 가능한 위치여야 한다. 다른 사용자가 부모 디렉터리 전체를 교체할 수 있는 환경이나 악성 파일시스템을 방어하는 capability sandbox는 아니다. 목적지 파일 이름 자체의 생성 경합은 no-clobber로 방어한다. 입력 심볼릭 링크는 읽은 대상 handle을 기준으로 검사하고, 출력 심볼릭 링크는 거부한다.

실패·취소에는 임시 디렉터리를 명시적으로 닫아 잔여 파일을 정리하며 정리 오류를 보고한다. 커밋 후 디렉터리 동기화·정리 오류는 결과가 이미 저장되었음을 메시지에 명시한다. 커밋 후 취소는 저장 파일을 삭제하지 않는다. 크래시 때 `.withcrypt-*` 잔여물이 남을 수 있으며 수동 제거가 필요할 수 있다. SSD의 보안 삭제를 보장하지 않는다.

## 비밀 수명과 사용자 인터페이스

비밀번호·master·저장 PRK·파생 키·청크 버퍼·Argon2 작업 메모리에 zeroize를 사용한다. 라이브러리 내부의 HKDF/HMAC 상태, UI 입력 이벤트·IME·문자열 재할당, 레지스터·컴파일러·OS 복사본까지 완전 삭제된다는 보장은 없다. CLI는 crossterm으로 프롬프트 출력 전 에코를 끄고 rpassword로 읽으며 RAII로 터미널 상태를 복구한다. GUI 비밀번호 필드는 프레임마다 undo 기록을 비운다. GUI는 저장 기능을 사용하지 않고 작업 시작 시 비밀번호 소유권을 작업 스레드로 옮긴다. UI 작업 수는 하나로 제한한다. Argon2 내부에서는 취소할 수 없고 전후 경계에서 확인한다.

파일 크기 및 레코드 길이를 숨기지 않는다. 파일명은 META에 암호화되지만 사용자 지정 출력 경로 자체는 운영체제에 보인다. 악성 OS·관리자·키로거·클립보드 감시·메모리 덤프는 범위 밖이다. GUI 비밀번호 표시를 켜면 화면과 접근성 도구에 보일 수 있다.
